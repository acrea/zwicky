# zwicky

zwicky is a browser-only tool for morphological analysis, named after Fritz Zwicky. A **space** states a problem, spans a box of **dimensions** (rows) × **parameters** (cells), marks what is already **fixed** or **out**, composes **options** by picking from what is still open, and rates the options against weighted **criteria**. A space is saved as one plain-Markdown file, `<name>.zwicky.md`.

This skill was generated by zwicky {{VERSION}} and covers file format version 2. The full specification is at the end of this file. It is the contract: where this guidance and the specification seem to differ, the specification wins.

## Reading a space

When asked to explain or review a file, go through it in this order:

1. **Goal:** the note under `# Problem`.
2. **Frame:** the `{fixed}` parameters (already decided, and every option has them) and the `{out}` parameters (excluded). Their notes say why, and who decided.
3. **Open space:** the remaining parameters per dimension. With one pick per dimension there are (open parameters of dimension 1) × (open parameters of dimension 2) × … combinations, which shows why a box needs options, not lists.
4. **Options:** each option is a path through the box: the parameters whose tag lists its id, plus every fixed parameter. An option can pick 0, 1 or several parameters per dimension. `extends=O<n>` marks a later stage of another option.
5. **Evaluation:** compute each option's weighted score with the formula under *Scoring*, rank the options, and say which criteria are still unrated. Unrated is not zero.

Point out what looks weak: dimensions that are not independent of each other, a dimension with a single open parameter (often a constraint in disguise, so suggest `{fixed}`), options that pick nothing in an important dimension, near-identical options, criteria that do not tell the options apart, and scores without a rationale.

## Creating a space

Build it from the user's input: workshop notes, interviews, a conversation, a document. Work in this order:

1. **Problem:** one question as the goal ("Which … should we …?", "How might we …?"), with context in the same note.
2. **Dimensions:** usually 4 to 10 independent aspects of a solution, each titled with a short buzzword ("Drivetrain", "Target group"). Every dimension gets 2 to 7 parameters: concrete, distinct alternatives, each a short single-line title. Rows may differ in length.
3. **Frame:** mark what the input says is already decided as `{fixed}`, and what it rules out as `{out}`, each with a note giving the reason and who decided. Do not invent decisions. If you infer one, write "Assumption: …" in the note, or leave the parameter open.
4. **Options:** usually 2 to 5 coherent, clearly different options, each a `## O<n> Title` heading numbered 1, 2, 3 … in order, with a note on the idea behind it. Record the picks as tags on the parameters (`- Electric {O1 O3}`), typically one per dimension. Use `{extends=O<n>}` for staged solutions (version 1, then an extension). After 8 options the colours repeat.
5. **Criteria:** usually 3 to 6, each `## C<n> Title`, weighted 0 to 10 (`{w=3}`; weight 1 is the default and is not written). The note says what "great" looks like.
6. **Ratings:** only where the input gives a basis. Put the rationale or the assumption in the rating's note. Leave a rating out rather than guess, or write `- C2: ?` with a note when there is an open question.

Write titles and notes in the user's language. The structure stays in English exactly as specified: the section headings (`# Problem`, `# Box`, `# Options`, `# Criteria`, `# Ratings`, `# Notes`), the front matter keys and the tag tokens (`fixed`, `out`, `O1`, `extends=O1`, `colour=3`, `w=2`).

## Editing a space

- **Change only what was asked.** Keep everything else exactly as it is: notes, unknown tag tokens, extra front matter keys and the `# Notes` section.
- **Add an option** at the end as the next number, add its id to the tags of the parameters it picks, and add its block under `# Ratings` if it gets ratings.
- **Option ids follow the order of the options.** When you insert, delete or move an option, renumber all options to 1, 2, 3 … in their new order and rewrite every reference: pick tags, `# Ratings` headings and `extends=`. An option keeps its colour when its number changes: if an option that is not an extension moves away from its number, give it `{colour=<k>}` with its old colour (the usual colour of `O<n>` is ((n − 1) mod 8) + 1, unless it already has a colour tag), and drop a colour tag that equals the usual colour of its new number.
- **Delete an option** with its heading, its id in every pick tag, its ratings block and any `extends=` pointing to it, then renumber.
- **Criterion ids never change.** A new criterion gets the highest id + 1. Deleting a criterion deletes its rating lines too.
- **Mark a parameter** `{fixed}` or `{out}` by replacing its pick tags: fixed and out parameters carry no picks.
- **Rename an option** in its heading and in its `# Ratings` heading.
- Do not set `updated`. zwicky writes it when the file is saved.

## Answering

- Give back the **complete file** in canonical form, never a fragment or a diff (unless the user asks for one). Put it in a single fenced code block marked `markdown`. If you can write files, save it as `<slug>.zwicky.md`: the title, lower case, with accents removed and every run of other characters turned into `-`.
- Tell the user how to open it: in zwicky, *File → Import from text* (paste) or *File → Open* (file). zwicky lists anything it had to correct.
- Notes and titles are plain text. Do not use Markdown formatting inside them.

### Checklist

Before you answer, check that:

- The front matter has `zwicky: 2`, and every score lies on its `scale` (default `1-5`).
- Option ids run O1, O2, O3 … in order, without gaps, and every pick and rating refers to an existing option.
- No parameter is both picked and `{fixed}` or `{out}`.
- Rating lines refer to existing criteria and hold whole numbers or `?`.
- `extends=` points to another existing option, and the links form no loop.
- Every title is a single line and does not end in a `{…}` group of its own; the only trailing `{…}` is the tag group.
- The layout is canonical: one blank line before every `#` and `##` heading and nowhere else, notes directly under their heading or item, list-item notes indented by two spaces (`  > `), bullets written as `- `.
